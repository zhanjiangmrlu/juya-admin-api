# juya-admin 缺失管理能力补全设计

## 1. 背景与目标

`juya-admin` 已覆盖登录页和 A01–A26，但当前接口契约没有完整覆盖已经确认的后台需求。前端因此将 13 项能力声明为 `pending`，并在联系资料、权益、活动、反馈、内容生产、媒体任务和统计页面显示“接口待接入”。

本次工作补齐需求文档已经明确、但尚未形成端到端闭环的能力。完成后：

- `juya-admin-api` 提供真实的管理查询、详情、编辑和命令接口。
- `juya-miniapp-api` 继续拥有用户档案和联系方式，仅通过 HMAC 内部接口向管理服务提供必要能力。
- `juya-admin` 使用生成契约和业务 adapter 调用真实接口。
- A01–A26 不再因为需求内能力缺失而展示“接口待接入”。
- 每个批次均可独立运行、验证、回滚和提交。

## 2. 范围与非目标

### 2.1 本次范围

- 用户学习概况、联系状态、敏感复制审计、联系更正列表、详情和处理。
- 正式权益、限时权益和统一权益列表及详情。
- 活动列表、草稿编辑、版本、容量和生命周期命令。
- 反馈列表、筛选、完整时间线、截图临时地址和内部备注。
- 内容列表、场景详情、结构化编辑、配置读取和管理员预览。
- OCR 任务、校对保存、音频版本、批量任务和草稿回收站。
- 日、周、月汇总统计查询。
- OpenAPI、生成类型、前端 adapter、页面状态和端到端验收同步。

### 2.2 非目标

- 不改变已确认的产品规则、A01–A26 信息架构或视觉设计。
- 不引入新的微服务、消息系统、数据库或前端状态框架。
- 不把用户档案和联系方式的数据所有权迁移到 `juya-admin-api`。
- 不使用演示数据伪装生产成功状态。
- 不增加多管理员、批量权益授予、交易、支付或复杂审批流。

## 3. 架构与数据边界

### 3.1 服务职责

- `juya-admin` 只调用 `/api/v1/admin/**`，不调用内部接口或数据库。
- `juya-admin-api` 是管理端唯一入口，拥有内容、活动、权益、反馈、媒体任务、统计和管理审计。
- `juya-miniapp-api` 拥有用户档案、联系方式和联系更正数据。
- 跨服务调用沿用 VPC + HMAC-SHA256、时间戳和 nonce 防重放；浏览器不接触内部签名密钥。

### 3.2 现有能力复用

- 复用现有 Cookie 会话、CSRF、幂等记录、统一错误体和审计基础设施。
- 复用已有内容、权益、反馈、媒体、统计表和领域服务。
- 复用 `juya-miniapp-api` 已有的用户搜索、用户详情、联系状态更新、核对变更和更正决定内部接口。
- 复用现有 OCR/TTS provider 协议、OSS 私有对象和 Celery 任务框架。
- 仅当现有 schema 无法表达版本、内部备注、任务状态、审计或必要索引时增加向后兼容迁移。

### 3.3 查询契约

- 管理列表统一返回 `items`、`page`、`page_size` 和 `total`，支持白名单筛选和排序。
- 敏感查询使用 `Cache-Control: no-store`；完整微信号不进入 URL、日志、统计或浏览器持久化。
- 编辑型资源返回 `version`；更新请求携带 `expected_version`，冲突返回 `409` 并附服务端当前版本。
- 详情接口返回页面一次渲染所需的聚合视图，避免页面自行拼接相互矛盾的状态。

### 3.4 命令契约

- 高风险命令使用明确的 `/commands/{operation}` 子资源。
- 写请求要求 CSRF；可重试命令要求 `X-Idempotency-Key`。
- 服务端重新校验当前状态、容量、版本和权限，前端禁用按钮不替代服务端规则。
- 成功命令在同一事务中保存业务操作记录；涉及敏感查看、复制或跨服务修改时追加管理审计。

## 4. 分批交付

### 4.1 第一批：用户与联系资料（A02–A04）

补齐用户学习概况、联系状态修改、微信号变更核对、敏感复制审计、联系更正列表、详情、批准和拒绝。

`juya-miniapp-api` 增加联系更正列表/详情及学习概况内部查询；`juya-admin-api` 扩展内部客户端并提供管理端聚合接口。完整微信号按需求在已认证的用户列表、详情和更正页直接返回，相关响应强制 `no-store`，查看、复制、修改和更正处理均写入审计。

### 4.2 第二批：权益与活动（A05–A12）

补齐统一权益列表、正式/限时权益详情、内容包查询、活动列表、草稿编辑、版本复制、启用、暂停、恢复、结束、归档和容量调整。

活动首次成功开通后锁定时长、场景顺序和启动窗口；容量只能调整到不低于累计开通人数。权益详情始终由服务端返回当前状态和可用操作。

### 4.3 第三批：反馈闭环（A14–A16）

补齐反馈列表和筛选、完整时间线、截图管理端临时地址及内部备注。现有开始处理、要求补充、回复和关闭命令保持状态机、幂等和 SLA 规则。

截图临时地址仅对管理员会话签发，默认短期有效且不进入日志；内部备注不发送给用户。

### 4.4 第四批：内容目录与编辑（A17、A20、A22、A23）

补齐内容列表、场景详情、revision 详情、结构化保存、开放场景/预览/学习模块配置读取和管理员预览。

人工版本与 OCR 候选分离；编辑保存使用乐观锁。管理员预览不创建用户进度，也不复用受限用户预览接口。

### 4.5 第五批：OCR、音频和批量任务（A18、A19、A21、A24）

将现有 OCR/TTS 任务服务接入 SQL repository、Celery 和管理路由，补齐任务创建、状态查询、候选读取、人工确认、重试和取消。补齐音频目标/版本列表、生成、上传、确认和回退，以及草稿回收站和通用批量任务。

任务单项失败不影响其他项；重试不覆盖人工版本；批量任务最多 500 项，音频批次最多 300 个，图片单批最多 30 张且同系列、同模板。

### 4.6 第六批：统计与全量验收（A01、A13、A25、A26）

补齐按日、周、月的汇总统计查询，继续只返回去标识化聚合。复核工作台、待办和系统配置对新增能力的联动，完成 A01–A26 双视口、主业务链路和接口覆盖验收。

## 5. 前端接入

- 每批从实际 FastAPI `app.openapi()` 更新固定 OpenAPI 快照并重新生成 TypeScript 类型。
- 页面继续通过 `composable → adapter → API client` 访问，不直接使用生成 DTO。
- 将该批能力从 `pending` 改为 `available` 的前提是：真实路由存在、adapter 已接入、页面具备加载/空/错误/成功状态且测试通过。
- 保留现有路由、表单规则、确认对话框和视觉结构，仅用真实数据替换占位内容。
- 列表筛选可恢复；完整微信号搜索继续使用 POST 正文，不进入 URL。
- `401` 清除敏感状态并跳转登录；`409` 保留本地草稿并展示服务端版本；`422` 映射字段错误；`429` 展示重试时间；`5xx` 展示 Request ID。

## 6. 数据迁移与兼容

- 新迁移只向前追加，不修改或重写已经发布的迁移。
- 新字段优先可空或提供安全默认值，随后由服务层逐步写入。
- 为管理列表常用筛选、状态、时间和外键增加组合索引，避免全表扫描。
- OpenAPI 变更保持已有接口兼容；新增字段采用向后兼容方式，现有响应字段不改名。
- 不删除现有 `pending` 组件，直到所有路由都完成；最终确认无页面引用后再决定是否清理。

## 7. 测试与验收

每批严格采用红—绿—重构：

1. 先增加失败的领域、repository、路由或前端行为测试。
2. 运行目标测试并确认因能力缺失而失败。
3. 实现最小功能并让目标测试通过。
4. 运行所属项目完整测试和质量门禁。
5. 使用真实本地服务执行关键 HTTP 与浏览器链路。

后端覆盖：

- 领域状态机、边界值、容量、版本冲突和幂等。
- MySQL repository、事务、行锁、分页和筛选。
- 路由鉴权、CSRF、HMAC、敏感响应和统一错误。
- OpenAPI 路由清单测试，确保设计内接口没有再次遗漏。

前端覆盖：

- adapter 路径、请求体、错误映射和取消请求。
- 页面加载、空、错误、冲突和成功状态。
- 敏感数据不进入 URL 和持久化。
- A01–A26 在 1440×900 和 1280×800 的关键交互与横向溢出。

每批完成后分别执行对应仓库门禁。最终至少执行：

- `juya-admin-api`：Ruff、格式检查、mypy、pytest、MySQL 集成测试和 OpenAPI 清单检查。
- `juya-miniapp-api`：Ruff、格式检查、mypy、pytest，以及新增内部接口契约测试。
- `juya-admin`：`pnpm check`、`pnpm test -- --maxWorkers=1`、`pnpm build`、关键 Playwright E2E 和 `git diff --check`。

## 8. 提交与批次门禁

- 三个仓库均直接在当前 `main` 分支开发。
- 每个批次按仓库形成独立中文 Conventional Commit；一个提交不混入下一批内容。
- 一批只有在后端接口、OpenAPI、前端接入和该批验证全部完成后才算结束。
- 若完整测试存在与当前批次无关的基线失败，报告具体测试和证据，不把聚焦测试成功描述为全量成功。
- 批次遇到跨服务契约阻塞时先完成契约测试和双方实现，不以临时 mock 绕过。

## 9. 最终完成标准

- 需求范围内的 13 项 `pending` 能力全部由真实接口实现并标记为 `available`。
- A01–A26 不再展示需求内能力的“接口待接入”文案，也不发送未知请求。
- 联系资料、权益、活动、反馈、内容、媒体任务和统计均有可执行的管理闭环。
- 所有敏感操作可审计，所有高风险命令具备 CSRF、幂等和服务端状态校验。
- OpenAPI 路由清单覆盖书面设计，生成类型与实际应用一致。
- 三个仓库的约定质量门禁和最终端到端验收均有新鲜执行证据。
